# 看屏幕

frame 的一个新模式：框住屏幕上任意一块，AI 一直看着，用语音告诉你怎么做；需要时经你同意，直接在你框的那块里替你操作。

> 这份文档是需求锁定后的方案。**M0 自检、M1（取景 + 框选界面）、整屏实时观看、动作层都已实现**；
> 画面标注、本地 OCR、跨平台还没做。
>
> **补充（2026-10-20）**：除了框选一块，现在还能「看整个屏幕」——覆盖所有显示器，
> 每 2 秒抓一帧、画面变了才更新；**开启前必须先点同意**，随时可停。
> 它不会自己开口，你说话时看到的是当下画面。

---

## 一、需求结论

| 维度 | 结论 |
| --- | --- |
| 框什么 | 屏幕上的任意区域。没有固定对象，什么突然不会就框什么 |
| 画面来源 | 本机截屏。**不走浏览器的屏幕共享**（理由见第三节） |
| 授权 | 框完先问「要不要让它看这块」，你同意它才看 |
| 看多久 | 一直看，像屏幕共享那样实时 |
| 怎么用它 | 语音指导 → 问你要不要它上手 → 你同意才动手 → 动手时你随时能打断 |
| 确认方式 | **语音问，你口头答应** |
| 模型看不了图 | 本地 OCR 兜底，把画面里的字抠出来转成文本 |
| 操作范围 | 只在你框的那块里，框外一律不动 |
| 没回应时 | 3 分钟没开口就自动结束，停止截屏、释放麦克风、清掉框选 |
| 入口 | 切回 frame 窗口，点面板上的按钮 |
| 平台 | 第一版只做 Windows，取景和动作抽象成接口 |

## 二、完整流程

```
① 你在 frame 界面点「框选」
        ↓
② 本机截一张全屏图，铺在网页上
        ↓
③ 你在图上拖出一个框
        ↓
④ 弹一句：要不要让它看这块？          ← 你说的「询问是否共享」
        ↓ 你同意
⑤ 开始看：本机按这个坐标持续截图
   画面没变就不发；变了才发给模型（最快 1.5 秒一次）
   你说话时强制发一帧最新的
        ↓
⑥ 它用语音告诉你该怎么做
   （同时在画面上画箭头、圈重点、标序号）
        ↓
⑦ 它觉得需要上手 → 语音问你「要我帮你点这个吗」
        ↓ 你说「好」
⑧ 动作前先在画面上高亮它要点哪儿，然后才真的点
   一次只做一个动作，做完立刻看结果
        ↓
⑨ 你随时开口 → 打断 → 停止后续动作
```

第 ④ 步是**纯软件的授权**，不是浏览器的屏幕共享弹窗。这一点是整份方案里最关键的判断，下一节说清楚。

### 空闲自动退出

看屏幕模式下同样适用：**用户 3 分钟没开口就自动结束**，停止截屏、释放麦克风。

额外有一条：退出时**框选区域一起清掉**。不然它会停在"还盯着那块"的状态，
下次打开你会以为它还在看。要再看就重新框一次。

（这套空闲退出的机制已经在语音对话里实现了，看屏幕直接复用，不用另写一套。）

## 三、关键判断：不要用浏览器的屏幕共享

网页想拿到屏幕画面，只有一条路：`getDisplayMedia()`。它会弹出系统窗口让你选「共享哪个屏幕 / 哪个窗口」。这条路有两个硬伤：

1. **顺序是反的。** 你要的是「先框选，再问要不要共享」。但浏览器必须先共享才有画面，你没画面就没法框。
2. **每次刷新页面都要重新共享一次。** 一个随手用的功能，每次用之前先过一遍系统弹窗，摩擦太大。

**但 frame 是本地跑的。** Next.js 的 Route Handler 就在你自己电脑上，它可以直接截屏 —— 不需要经过浏览器。

所以顺序可以变成你要的那样：**先截全屏 → 你在图上拖框 → 再问要不要让它看**。

这和之前砍掉「本地桥」是同一个判断：本地运行时，服务端就是本机进程，不需要再翻一道墙出去。

顺带的好处：

- 不用装任何东西
- 不受「共享哪个窗口」的限制，整个虚拟桌面都能框
- 多屏也是自然的（截的是虚拟桌面整体）

## 四、三层结构

### 取景层（本机，不碰网络）

| 做什么 | 怎么做 |
| --- | --- |
| 截全屏给你拖框 | 一次性，截虚拟桌面 |
| 持续截框内区域 | 按坐标裁剪，只截那一块 |
| 判断画面变没变 | 本地算 dHash 感知哈希，比像素差抗噪 |
| 往上送 | 只有变化明显时才送，附上变化前后的图 |

**变化检测必须在本地做。** 如果每帧都发给模型，「一直看」会变成持续烧钱。本地先比对，画面静止的时候一分钱不花。

dHash 那套逻辑 SnapMind 里已经验证过（64bit 差值哈希 + 汉明距离），直接搬。

### 理解层（模型）

两条路，同一套提示词：

| 模型 | 走哪条 |
| --- | --- |
| 支持视觉（GPT-4o / Qwen-VL / GLM-4V…） | 直接把框内的图发过去 |
| 纯文本（DeepSeek / Kimi…） | 本地 OCR 抠出文字 + 位置，拼成结构化文本发过去 |

第二条是「不管模型支不支持都能用」这条原则在看屏幕上的落地。

**OCR 不只是文字。** 光有字不够 —— 「下一步点哪里」需要知道哪个字在哪个位置。
所以 OCR 结果要带上坐标和相对位置，拼成类似：

```
[框内画面 800x600]
文字块（按位置从上到下）：
  (120,80)  登录失败：验证码错误
  (120,140) 重新获取验证码
  (200,200) [按钮] 确定
```

这样纯文本模型也能说「点那个『重新获取验证码』」。

### 动作层（本机）

| 动作 | 说明 |
| --- | --- |
| 点击 | 坐标必须落在框内，框外直接拒 |
| 输入文字 | 先点进输入框，再输入 |
| 按键 | 回车、Tab 这类 |

三个硬约束：

1. **坐标锁死在框里。** 框外的坐标一律拒绝执行，不做任何"例外处理"。
2. **一次只做一个动作。** 不做「连点五次」这种批量操作，每个动作之间都能被打断。
3. **动作前先高亮。** 在预览画面上圈出它要点哪里，你看得见再点。这既是提示也是最后一道确认。

## 五、成本控制

「一直看」不等于「一直发」。四层过滤，和 SnapMind 一样：

```
① 画面没变        → 不发
② 变了但变化很小   → 不发（汉明距离阈值）
③ 变化明显但刚发过 → 不发（最快 1.5 秒一次）
④ 一分钟内发太多   → 降频
```

外加一条：**你说话的时候强制发一帧最新的**。这样你问「这个怎么办」的时候，它看到的一定是当下的画面，而不是几秒前的。

结果是：画面静止时基本不花钱，只有真的在动（视频、动画、你在操作）才产生费用。界面上会实时显示这个会话花了多少。

## 六、安全

你选的「语音问、口头答应」是三种确认方式里最弱的一种 —— 语音识别错一次，它就直接动手了。而且「好」这个字太容易被环境里的声音触发。

这个选择我尊重，但必须补几道防线，不然它会撞上你自己定的红线（永不删除重要信息）。

| # | 防线 | 为什么 |
| --- | --- | --- |
| 1 | **坐标锁死在框里** | 误操作的影响范围被你框的大小限死。框得小，风险就小 |
| 2 | **动作前高亮目标** | 语音说的同时画面上圈出来，你有机会看到"不对"并打断 |
| 3 | **一次一个动作** | 不做批量连点，每个动作之间都是可打断点 |
| 4 | **危险词强制弹窗** | 框内文字出现「删除 / 清空 / 卸载 / 格式化 / 覆盖 / 重置」这类词时，**口头确认作废**，必须点弹窗才能继续 |
| 5 | **随时可打断** | 复用语音会话已有的轮次号机制，打断后剩余动作全部作废 |
| 6 | **操作留痕** | 每个动作进操作流水：点了哪、输入了什么、什么时候。可查 |

**第 4 条是对你的选择的补丁。** 你选了口头确认，我照做，但涉及删除类操作时降级成弹窗确认 —— 这条不商量。语音误识别的代价和点一下弹窗的代价差太远。

另外，看屏幕这个能力**整体是一个开关**，默认关闭。不想用的时候，本机一次都不会截屏。

## 七、界面

主界面加一个「看屏幕」面板，三种状态：

**空闲**
```
┌─────────────────────────────┐
│  看屏幕                      │
│  ┌─────┐                    │
│  │     │  还没框过           │
│  └─────┘  [ 框一块 ]         │
└─────────────────────────────┘
```

**框选中** —— 全屏截图铺满，十字准星，拖出选框，松手出尺寸和坐标。

**看护中** —— 一个小预览窗，显示框内的实时画面，加三个状态字：在看 / 在说 / 在操作，一个「停止」按钮。操作时预览窗里会高亮它要点的地方。

视觉上沿用已有的母题（同心圆 + 刻度环），选框用方框 —— 和品牌标记一致。

## 八、平台

第一版**只做 Windows**（你自己用）。取景层和动作层抽象成接口，后面补别的平台。

## 九、不做什么

- **不做常驻后台截屏。** 没框选的时候一次都不截。这不是配置项，是代码里就不做。
- **不做多区域同时看。** 第一版一个框，换框就换目标。
- **不做录制回放。** 画面只在内存里过一遍，不落盘。
- **不让 AI 自己决定要不要操作。** 所有动作都要先问过你。
- **不做框外操作。** 没有"这次例外"。

## 十、一个我没能验证的点

取景和动作要调系统能力（.NET 截屏、SendInput 模拟输入）。**我这边沙箱把 `Add-Type` 禁了，PowerShell 工具也报错，所以这两件事我没法在交付前实测。**

所以第一步不是写功能，是写一个自检：

```bash
npm run doctor
```

它会实际做四件事，把结果打出来：

1. 能不能截一张全屏图（打印分辨率和耗时）
2. 能不能按坐标裁剪出框内区域
3. 能不能读到当前鼠标位置（验证 P/Invoke 通路，只读不动）
4. 能不能模拟一次输入（在你确认后才做，比如在记事本里敲一个字）

**四项都过，才往下做。** 任何一项不过，方案就得换实现（比如改用 Node 原生模块，或者退回"只能看不能操作"）。

这是整份方案里唯一有真实风险的地方，所以放在最前面验证。
